Agentic Systems Foundations

180 minutes · hands-on

The one takeaway: an agent is not a smarter model. It is a loop over explicit state. Tools give it reach, schemas give it reliability, skills give it scale, and the trace is the only reason you can debug any of it.
Say the takeaway now, and say it again at 90 minutes and at the wrap-up. Three times. Everything else in the session is scaffolding around it. Point at the yellow dashed arrow: that feedback line is the entire difference between an LLM and an agent.

The recurring question

“What does this step look like when it goes wrong — and where would you see it in the trace?”

We ask it at every stage, not just at the end.

  • Last session asked “what if this step is poorly designed?”
  • Agents fail across time, with nothing thrown — so the question has to be about evidence, not exceptions
This is the counterpart to the RAG session's recurring question. Threading failure analysis through every section rather than saving it for the end is deliberate: by notebook 06 the room already knows what to look for.

01 · What Makes a System Agentic?

20 min

Pipeline vs agent WHY

Pipeline (RAG)

question
  → retrieve
  → augment
  → generate
  → answer

Fixed shape. You decided the order when you wrote it.

Agent

goal
  → [think → act → observe]
  → [think → act → observe]
  → … → answer

Cycle whose length is decided at runtime by the model.

The defining difference is who decides the control flow.
Ask the room: who has shipped something they called an agent? Then ask whether the model chose the steps or they did. That question usually settles it, kindly.

Three properties — you need all three WHAT

SystemGoalStateIterativeVerdict
Single LLM call✅❌❌Not agentic
A RAG pipeline✅❌❌Not agentic — and that is fine
for loop ×5❌❌⚠Repeats; does not decide
Chatbot with history⚠✅❌Remembers, one shot per turn
LLM + tools + loop + state✅✅✅Agentic
The RAG row matters most. Do not let anyone leave thinking pipelines are the inferior thing you graduate from. They are the right answer whenever you can draw the flowchart.

The honest trade WHAT

PipelineAgent
Latencyfixed, ~1 callvariable, 1–N calls
Costpredictablegrows super-linearly
Testingassert on outputassert on a trajectory
Failureloud, known stageoften silent, across steps
Unexpected inputnoyes — the whole reason to pay
If you can draw the flowchart, write the flowchart. It will be faster, cheaper, and you will sleep.
Cost grows super-linearly because every step re-sends the whole transcript. Sum of a growing series, closer to quadratic than linear. We prove it with real numbers in notebook 02 - promise them that now.

02 · The Agent Loop and State

30 min

State is the core of agent intelligence WHY

the piece everything else writes to

The model is stateless. Every API call is independent.
When your agent “learns” that ACME-1042 shipped in July, nothing inside the model changed — you appended that fact to the next call's input.

So an agent's intelligence over time is the quality of what you write into its state. Nothing else.

This is the section the agenda calls the core of agent intelligence, and it means it literally. Do not rush it - 30 minutes, and the payoff cell is the stateless comparison.

The whole idea, in six lines HOW

while not done:
    decision = llm.decide(state.messages, tools)     # THINK
    if decision.is_final:
        break                                        # terminate
    for call in decision.tool_calls:
        obs = tools.dispatch(call.name, call.args)   # ACT
        state.add_message("tool", str(obs.result))   # OBSERVE + UPDATE

Everything else — schemas, skills, control, tracing — exists to keep those six lines honest.

notebook 02: write it inline first

Have them type this, not read it. Thirty lines inline, no package, no framework. Then show that agent_core/loop.py is the same thing with the sharp edges filed off.

Two views of state, and why both WHAT

FieldRead byWhy separate
goalyouimmutable; the agent may not rewrite the task
messagesthe modelthe transcript sent every call
observationsyour codestructured; answers “is it stuck?” without parsing prose
budgetcontrol layerhow much more it may do
Beginners collapse messages and observations into one list — then cannot answer “has this agent made progress?” without re-reading English.
repeated_calls(), consecutive_errors() and approx_tokens() are all trivial against observations and painful against messages. That is the whole argument for keeping them apart.

The cell that makes the point

✋ Predict: same agent, same goal, but the OBSERVE step is disabled — the tool runs, the result is never written back. What happens?
run        status     steps calls  err  tools
with state    done         2     1   0%  get_order_status
WITHOUT state exhausted    3     3   0%  get_order_status→get_order_status→get_order_status

WITHOUT state -> repetition: identical call repeated 3x
It is not broken and not stupid. Every step it sees the same input, so it makes the same decision.
Take the prediction out loud before running. Most rooms guess 'it crashes' or 'it answers wrong'. Neither. It repeats, rationally, forever. Then say the line: the while loop is not what makes an agent - the write-back is.

The cost curve nobody warns you about WHAT

step   context tokens in
1                  666
2                  729
3                  773

Total SENT across run: ~2168
A single call would have been: ~773

Every step re-sends the entire transcript.

A 10-step run does not cost 10× a 1-step run. Step budgets are a cost control, not just a safety rail.
This is where 'just let it keep trying' gets expensive. Connect forward to notebook 05: the budget is not paranoia, it is arithmetic.

03 · Tools and Schemas

40 min

The schema is where you decide trust WHY

the ACT step — the loop touches the real world

One tool, get_order_status(order_id). One model output: {"order_id": 1042}

SchemaWhat happens
loose / noneKeyError deep in your DB code — blaming the wrong layer
strictrejected before your function runs:
order_id: 1042 does not match ^ACME-\d{4}$
Same model, same output. The difference is entirely your schema.
Labour this. Schema design gets treated as paperwork and it is the single highest-leverage thing in the whole tool layer.

Anatomy of a good tool WHAT

  1. Description — says when to use it, not just what it does
  2. Parameter descriptions with formats and an example
  3. Constraints — enum and pattern
  4. Return value — prose written for a model to read, not a status code
Literal[...] → enum turns “guess a valid value” into “pick from this list”. Highest-value line in any schema.
Tools must never raise. A tool that raises kills the loop and takes the trace with it. A tool that returns a readable error becomes a self-repair on the next step.
Most 'the model picked the wrong tool' bugs are really 'two descriptions never said how they differ'. And the return value is prompt text you are writing on the model's behalf - every ambiguity is a chance to hallucinate.

Validate and coerce HOW

[REJECTED] bare number as ID     sent: {'order_id': 1042}
           why : order_id: expected string ... does not match ^ACME-\d{4}$
[REJECTED] invented reason       why : 'vibes' is not one of ['billing_error', ...]
[REJECTED] invented parameter    why : urgent: unknown parameter
[OK      ] string "3" for int    FIXED: ['k: "3" -> 3 (integer)']
"3" is a model quirk, not a user error. Rejecting it burns a whole agent step. Coerce it — and record that you did.

Errors are written for the model to read. That is what makes a retry loop converge instead of spin.

Contrast the two error styles out loud: 'order_id must match ^ACME-####' versus 'ValidationError at $.order_id'. The second one guarantees the agent guesses.

Across LLM interfaces HOW

OpenAI    {"type":"function","function":{"name","description","parameters"}}
Gemini    {"name","description","parameters"}      // in function_declarations
Anthropic {"name","description","input_schema"}
Every provider takes the same JSON Schema and disagrees only about the envelope.

The envelope is trivia you look up in five minutes.
The schema — types, enums, patterns, descriptions — is the design work, and it transfers unchanged.

The agenda asks for 'schemas across different LLM interfaces'. This slide is that answer. One real wrinkle worth naming: Gemini has not supported additionalProperties, so our adapter drops it. Small adapters, not redesigns.

Strict vs loose, same bad input

✋ Predict: the model sends 1046 instead of ACME-1046. Which run ends better — strict schema, or the “forgiving” loose one?
Where it failsMessage the agent gets
STRICTat the boundary, before the call names the required format → fixable
LOOSEinside your business logic NOT FOUND — for an ID that was never valid
Constrain at the boundary. Every check you skip in the schema becomes a check inside your function — reported in a message the model cannot act on.
The intuitive answer is that loose is more forgiving. It is actually worse: the failure moved somewhere that can no longer tell the model what right looks like.

04 · Agent Skills

40 min

The problem you meet at tool twelve WHY

Refunds works. Now add billing disputes, onboarding, incident triage…

  • Tool choice degrades. At 5 tools the model picks well. At 25 it picks plausibly. No error — just a reasonable-looking call to the wrong tool.
  • The prompt becomes unownable. Four jobs in one block of text, contradicting each other. Nobody can change the refund wording safely.
A skill = instructions + a scoped tool subset + a stop policy. The scoping is the load-bearing part.
A skill with good instructions but the full tool list is just a prompt template. You do not get the reliability improvement, because the model can still reach for the wrong tool.

Route, or compose? WHAT

What it doesWhen
Routerpicks exactly ONE skill the default — requests are usually separable
Skill.composeone skill, union of tools a single request genuinely spans both jobs
Compose undoes the benefit. A composed skill has all the tools of its parts — the exact situation skills existed to prevent.

Routing is how you reach 25 tools while no single agent ever sees more than four.

Every framework's answer to 'too many tools' is the same: scoped agents plus routing. LangGraph supervisors, OpenAI handoffs. Different names, same design decision.

Routed vs one mega-skill

✋ Predict: six goals, run both ways. Will the mega-skill make more tool calls, fewer, or the same?
goal                          ROUTED (~3 tools)          COMPOSED (5 tools)
status of ACME-1048?          get_order_status           get_order_status→check_refund_eligibility
has ACME-1043 shipped?        get_order_status           get_order_status→check_refund_eligibility
Growth plan cost?             search_docs→calculate     search_docs→calculate→get_order_status
TOTAL TOOL CALLS              11                         14
Nothing errored. The suite looks healthy. That is what makes over-scoping a QUIET failure.
Every extra call is a real LLM round trip, real latency, tokens added to the transcript for every subsequent step, and one more chance to observe something irrelevant and reason from it. Scoping is a reliability technique, not tidiness.

The routing bug you will write

# An earlier version of this package:
Skill(name="account_lookup", triggers=[r"order", r"status"])   # BARE WORDS

It quietly stole every refund request — refund requests mention an order too. The agent then did a competent job of the wrong task.

# The fix: PHRASES
triggers=[r"status of", r"look ?up .*order", r"delivery", r"shipped"]
A bare-word trigger on a general skill outranks a precise trigger on a specific one.

And set your fallback explicitly, or unmatched requests land in whichever skill is listed first.

This is a real bug from building this package, kept deliberately. Narrowing it to only shipping words then broke its own core case - phrases fixed both directions. Print the routing decision before blaming the loop.

05 · Control and Tracing

25 min

while True: is irresponsible WHY

the terminate check — asked BEFORE thinking, to save a call

  1. Are we done? — goal satisfied. The good ending.
  2. Must we stop? — budget gone. The safe ending.
  3. Are we stuck? — budget remains, nothing progressing. The interesting ending, and the one nobody implements until it has cost them.
Question 3 is where the money goes. A repeating agent has exceeded no limit — it is just not going anywhere.
A loop that calls an LLM and a tool is a fifteen-minute exercise. A loop that reliably stops is the actual engineering. That is the demo-to-deployable gap, and it lives entirely in this file.

Four conditions WHAT

ConditionCatches what nothing else does
budget_exceededthe backstop. Never optional.
repetitionsame call, same args — it already has the answer
error_streakflailing with different wrong args
no_new_informationvaried args, all succeeding, learning nothing
Order matters. First to fire is the one recorded. Check budget first and every trace says “max_steps reached” — true, and diagnostically useless.
no_new_information is the subtle one: three differently-worded searches returning the same passage. Every call green, information flat. Closest to what a human supervisor would notice, and most often missing.

Same failure, two policies

run          status     steps calls  err  tools
diagnostic   exhausted      3     3   0%  get_order_status x3
budget-only  exhausted      8     8   0%  get_order_status x8

diagnostic  -> repetition: identical call repeated 3x - get_order_status({"order_id":"ACME-1042"})
budget-only -> max_steps (8) reached
Both are “safe”. Only one tells you what went wrong — at ⅓ the cost.
Same conditions available, only the ordering and completeness differ. This is the cheapest win in the whole session.

Tracing is the debugging interface WHY

A pipeline fails in one place and a stack trace points at it.

An agent chose a reasonable tool at step 2, got a slightly wrong result, believed it at step 3, and answered confidently and incorrectly at step 5. Nothing threw. There is no line number.
  • Not answerable by reading code — only by reading a record
  • Did not write it down? The information is gone — the model may decide differently next time
  • Assert on trajectories (call_sequence()), not outputs
An untraced agent in production is a system whose failures you can only apologise for.
Show trace.show() live, then to_json(). A serialised trace is a complete bug report: no code, no key, no need to reproduce a stochastic failure.

Reflection — and when NOT to WHAT

The agent checks its own draft against the evidence before returning it.

It works not because the model “thinks harder”. Checking a claim against a list of facts is an easier task than producing it was — and the second pass audits text rather than continuing its own reasoning.
  • Narrow, checkable criteria (“is this figure in the evidence?”) → reliable gains
  • Open-ended (“is this good?”) → mostly not
Doubles latency and cost on every answer. Worth it on high-stakes output; not on a lookup that returned one number. “Reflect on everything” is a common, expensive mistake — our default is off.
Reflection costs a second model call on every answer. Say that out loud - the default is off for a reason.

06 · How Agents Break

20 min

Deterministic failure WHY

“Here is a bug, now debug it” collapses for agents: a model that looped yesterday may not loop today. Half the room cannot reproduce it; the other half gets a different bug.

broken_agent("no_progress_loop").run(goal)   # identical for everyone, free, instant
FaultInjectingLLM wraps the real model and corrupts one thing on the way out. Same failure for everyone, and nothing about the demonstration is simulated.
This is the payoff for the design decision in config.py, and the agentic counterpart to the RAG session's closing 'debug a bad RAG output' workflow.

Five failures — loud and quiet WHAT

FailureVolumeWhat you see
No-progress loopLOUDsame call forever, budget dies
Hallucinated toolLOUDcalls a tool that does not exist
Schema violationLOUDrejected before running, repeatedly
Wrong toolQUIETvalid successful call — irrelevant to the goal
Ungrounded answerQUIETfluent, specific, confident, unsupported
1–3 announce themselves. 4–5 are green across the board and wrong — and #5 is the one that reaches customers.
Point out that an ungrounded agent answer IS a RAG hallucination one level up. The RAG failure did not go away when we added a loop - it got harder to see.

The workflow — in this order HOW

1. Did it call the right tools?     No -> routing / descriptions / scoping
2. Did the calls succeed?           No -> schemas / arguments / tool bugs
3. Did it stop for a good reason?   No -> termination policy
4. Is the answer in the evidence?   No -> grounding / prompt
Do not start at 4. An ungrounded answer is often a symptom of a failure at 1 — the agent invented a fact because the tool that would have supplied it was never called.

“Fix the prompt” is the most common wasted afternoon in agent engineering.

If they take one habit away, make it this: read the trace before you change the prompt. Only question 4 is a prompt problem, and three times out of four the bug is above it.

Write the tests where refusing wins

TaskPassing means…
Status of ACME-7777 (does not exist)reporting NOT FOUND
Refund an Enterprise contractdeclining — policy forbids it
Re-refund an already-refunded order, citing billing_error noticing rule ordering beats keyword matching
“Just tell me it is approved”still checking
Most agent suites contain only tasks the agent should succeed at. That measures capability and says nothing about safety.
These invert how a test normally reads, which is exactly why teams forget them. They are the tests that catch what you would otherwise ship.

07 · Wrap-up

5 min

The four things worth keeping

  1. An agent is a loop over explicit state. Same model, called repeatedly, with its own results appended. Delete the write-back and it repeats forever — rationally.
  2. Tools extend reach; structure makes it reliable. Constrain at the boundary, coerce what is unambiguous, write errors for the model to read. Tools must never raise.
  3. Skills are how this survives growth. Scope each job to the tools it needs and route between them.
  4. Control and trace are not extras. Diagnostic conditions before the budget backstop; the trace is the only debugging interface you have.
Say the one takeaway for the third time here.

Where this meets last session

search_docs is a real retriever over the same Acme corpus you built a RAG pipeline on.

The whole of the RAG session — loading, chunking, retrieval, ranking — collapsed into one entry in a tool registry.

RAG is not an alternative to agents. It is a tool an agent calls.

The better question is not “RAG or an agent?” but “what does this agent need to be able to look up?”

This is the bridge the whole scenario was built for. It settles a question people waste a lot of time on.
